## 1. Общая информация о проекте

**VK Tech Presentation Generator** — сервис автоматизированного создания презентаций на основе существующего PowerPoint-шаблона и текстового брифа.

Основная идея: пользователь не создаёт презентацию с нуля. Сервис получает готовый `.pptx`-шаблон, анализирует его визуальную структуру (цвета, шрифты, сетку, компоновки, плейсхолдеры), после чего формирует структуру новой презентации и размещает контент в соответствии с визуальной системой исходного шаблона.

Система состоит из следующих частей:

- парсер PowerPoint-шаблонов;
- модель дизайн-системы;
- модуль планирования содержания;
- Layout Engine;
- генераторы графиков и таблиц;
- модуль экспорта;
- модуль аудита;
- веб-интерфейс.

**Основной формат результата** — PowerPoint `.pptx`. Дополнительно предусмотрена генерация `.pdf` и `.html`.

**Ключевые возможности:**

- генерация презентации на основе произвольного шаблона;
- сохранение визуального стиля исходного шаблона;
- три варианта генерации;
- экспорт в редактируемые `.pptx` и `.html`;
- аудит и автоматическое исправление артефактов;
- подсветка проблемных участков для пользователя.

## 2. Архитектура проекта

Архитектура построена по модульному принципу. Каждый этап обработки имеет собственную ответственность и передаёт следующему этапу структурированные данные.

Входные объекты: PowerPoint-шаблон и текстовый бриф.

Последовательность обработки:

1. **Parser** анализирует шаблон → формирует `DesignSystem`.
2. **Content Planner** формирует `SlidePlan` (структуру будущих слайдов).
3. **Layout Engine** преобразует план в элементы с координатами, размерами и стилями.
4. **Slide Builder** собирает слайды.
5. **Audit** проверяет результат.
6. **Repair** исправляет найденные проблемы.
7. **Exporter** создаёт итоговые файлы `.pptx`, `.pdf`, `.html`.

Веб-интерфейс работает как пользовательский слой: позволяет загрузить шаблон, передать контент и бриф, запустить генерацию и получить ссылки на созданные варианты.

Такое разделение позволяет:

- тестировать компоненты независимо;
- заменять или расширять конкретный этап без полной переработки системы;
- масштабировать функциональность.

## 3. Модуль анализа шаблона (Parser)

**Точка входа:** `parser/parse_template.py`, функция `parse_template()`.

Последовательно запускает:

- `theme_parser.py` — анализ темы (цвета, шрифты);
- `master_parser.py` — анализ master-слайдов;
- `layout_parser.py` — анализ layouts;
- `slide_parser.py` — анализ существующих слайдов;
- `grid_extractor.py` — извлечение сетки;
- `pattern_clusterer.py` — кластеризация паттернов.

**Результат** — словарь с информацией:

- исходный файл;
- размер и формат слайдов;
- количество слайдов;
- количество layouts;
- цветовая палитра;
- типографика;
- сетка;
- паттерны;
- правила;
- логотип и другие ресурсы;
- `confidence`;
- ошибки отдельных этапов.

Парсер предусматривает частичную обработку ошибок: если один из этапов анализа не выполняется, используются значения по умолчанию, а информация об ошибке записывается в поле `errors`.

## 4. Модуль генерации презентации

**DesignSystem** — промежуточное представление визуальной системы исходного шаблона.

### Цвета

Из PowerPoint theme извлекаются цветовые значения и преобразуются в семантические токены:

- `primary`;
- `secondary`;
- `accent`;
- `text_primary`;
- `text_secondary`;
- `text_inverse`;
- `background`;
- `surface`.

Это позволяет генератору работать не с конкретными RGB-значениями, а с назначением цвета.

### Типографика

Из master и theme извлекаются используемые шрифты и размеры текста. Формируются роли:

- `slide_title`;
- `slide_subtitle`;
- `section_title`;
- `bullet`;
- `bullet_sub`;
- `chart_label`;
- `table_header`;
- `table_cell`;
- `footer`.

### Сетка

DesignSystem содержит:

- размеры слайда;
- safe area;
- отступы;
- колонки;
- gutter;
- вертикальные и горизонтальные направляющие.

### Паттерны

Layouts и существующие слайды группируются в паттерны. Для паттернов рассчитываются ограничения контента (например, допустимое количество bullet-пунктов).

## 5. Планирование содержания

**Компонент:** `generation/plan_content.py`.

Отвечает за подготовку структуры содержимого презентации на основе брифа и дизайн-системы.

Для AI-компонентов используются отдельные промпты в каталоге `prompts`, хранящиеся в отдельных Markdown-файлах. Например, `content_planner_v1.md` предназначен для планирования содержания.

Такое разделение позволяет изменять инструкции для модели отдельно от кода и сохранять разные версии.

---

## 6. Формирование компоновки

**Компонент:** `generation/layout_engine.py`.

Используется после определения содержания. Определяет, каким образом элементы будут размещены на слайде с учётом доступного пространства и характеристик исходной дизайн-системы.

Для выбора вариантов расположения предусмотрен отдельный промпт `layout_selector_v1.md`.

Результат работы этого этапа используется при непосредственной сборке слайда.

---

## 7. Построение слайдов

**Компонент:** `generation/slide_builder.py`.

Непосредственная сборка слайдов выполняется компонентом `slide_builder.py`. При создании слайда могут использоваться специализированные компоненты для различных типов объектов: графиков, таблиц, изображений.

Такое разделение упрощает расширение системы: при необходимости добавления нового типа визуального объекта соответствующий builder реализуется отдельно, без изменения всего механизма построения презентации.

Поддерживаемые типы элементов:

- текстовые блоки;
- графики;
- таблицы;
- диаграммы;
- пиктограммы;
- изображения (в отборочном этапе генерация изображений не выполняется).

## 8. Модуль аудита

**Каталог:** `audit/`.

Аудит проверяет результат генерации. Проверки разделены на **детерминированные** и **контекстные**.

### Детерминированный аудит (`audit/deterministic/`)

Проверки по чётким правилам, без использования AI. Работают быстро и предсказуемо.

| Проверка | Файл | Что проверяет | Пример проблемы |
|---|---|---|---|
| Границы | `bounds.py` | Выход объектов за safe area | Текст уехал за правый край |
| Пересечения | `overlap.py` | Наложение элементов | Картинка налезла на график |
| Типографика | `typography.py` | Размер шрифта | Шрифт 8pt |
| Цвета | `colors.py` | Контраст текста и фона | Белый текст на белом фоне |
| Плотность | `density.py` | Перегруз элементами | 20 пунктов на слайде |
| Целостность | `integrity.py` | Пустые слайды | Слайд без контента |

**Точка входа:** `audit/audit.py`, функция `run_audit()`.

### Результат

`AuditReport` со списком `Issue`:
- `slide` — номер слайда;
- `shape_id` — ID фигуры;
- `type` — тип проблемы;
- `severity` — `low` / `medium` / `high`;
- `message` — описание;
- `bbox` — координаты для подсветки в UI.

Подробнее — в `AUDIT.md`.

## 9. Визуальный аудит

**Каталог:** `audit/contextual/`.

Помимо детерминированных проверок предусмотрен контекстный аудит с использованием VLM (Vision-Language Model).

| Файл | Назначение |
|---|---|
| `vlm_audit.py` | Проведение визуальной проверки |
| `prompts.py` | Инструкции для VLM |
| `render.py` | Рендер слайда в изображение |

Процесс:

1. Слайд рендерится в изображение (PNG) — `render.py`.
2. Изображение передаётся VLM — `vlm_audit.py`.
3. Модель оценивает слайд: смысл, стиль, понятность, композицию.
4. Возвращается список проблем.

Использование двух типов проверок (детерминированные + VLM) позволяет сочетать программную проверку конкретных параметров с визуальным анализом готового слайда.

## 10. Исправление ошибок

**Компонент:** `audit/repair.py`.

Обрабатывает результаты аудита и исправляет обнаруженные проблемы:

- сдвиг объектов внутрь safe area;
- разнесение наложившихся элементов;
- увеличение шрифта до минимума;
- смена цвета на контрастный.

После исправления результат может быть проверен повторно — аудит запускается заново.

## 15. Pipeline

**Каталог:** `pipeline/`, основной файл — `pipeline/run.py`.

Pipeline используется для последовательного выполнения основных этапов обработки презентации:

1. Анализ шаблона.
2. Подготовка содержания.
3. Выбор компоновки.
4. Создание слайдов.
5. Проведение аудита.
6. Исправление обнаруженных проблем.
7. Подготовка итогового результата.

Pipeline выполняет роль координирующего компонента и объединяет независимые модули в единый процесс.

## 16. API

**Каталог:** `api/`, основной файл — `api/server.py`.

## 21. Входные данные

Основной входной формат — PowerPoint `.pptx`, используемый как шаблон.

Шаблон содержит визуальную структуру, которая анализируется parser'ом.

Каталог `data/templates` предназначен для хранения шаблонов презентаций.

Пользователь также передаёт:

- текстовый бриф (что должно быть в презентации);
- контекст (читатель презентации, потребитель);
- количество слайдов (по умолчанию 10–15, возможно до 5).

---

## 22. Выходные данные

Проект предусматривает экспорт сгенерированной презентации в нескольких форматах:

- `.pptx` — PowerPoint;
- `.pdf`;
- `.html`.

Компоненты экспорта находятся в каталоге `generation/export/`.

**Важно:** экспорт `.pptx` и `.html` должен быть **редактируемым** (не растром). Слайды должны содержать разметку, текстовые блоки, графики, таблицы — а не единую картинку.

Дополнительно предусмотрена генерация **трёх вариантов** презентации.

## 24. Особенности архитектуры

Главной особенностью проекта является **разделение анализа шаблона, генерации и проверки результата** на независимые части.

- **Parser** работает с исходным PowerPoint-файлом и формирует данные для генератора.
- **Generation** отвечает за создание содержимого и визуальную компоновку.
- **Audit** работает с результатом генерации и проверяет его на наличие проблем.
- **Shared** предоставляет единые структуры данных и вспомогательные функции.
- **Pipeline** связывает перечисленные части в единый процесс.

Такое устройство проекта позволяет:

- отдельно тестировать основные компоненты;
- при необходимости заменять или расширять конкретный этап без полной переработки системы;
- масштабировать функциональность;
- обеспечивать соответствие требованиям ТЗ.

## 26. Приложение. Аудит

Подробное описание модуля аудита — в `AUDIT.md`.
Отчёт об аудите — в `AUDIT_REPORT.md`.

### Краткая схема

```
Шаблон + Бриф → Генерация → [АУДИТ] → Исправление → Экспорт
```

### Виды аудита

- **Детерминированный** — проверки по чётким правилам (границы, наложения, типографика, цвета, плотность, целостность).
- **Контекстный** — проверки с использованием VLM (смысл, стиль, понятность, композиция).

### Результат

Список проблем (`Issue`) с координатами (`bbox`) для подсветки в UI.

### Использование

```
from audit.audit import run_audit
from audit.repair import repair

report = run_audit(presentation, design_system)
if report.has_issues:
    presentation = repair(presentation, report, design_system)
```

### Запуск тестов

```
pytest audit/tests
```
